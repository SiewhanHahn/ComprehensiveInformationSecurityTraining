# 撤回与晚订阅补投：通知顺序验收

基线 `20ff469`。实时撤回和定时补投使用同一条通知投递路径，对同一批接收者先写缺失的发布、后写撤回；去重键保留原通知 ID。通知中心按 ID 倒序，最新的是撤回。这只约束新投递的事件；**不重排旧库里已经写反的一对通知**。没有引入数据库迁移或更改 API。

| 订阅时间 | 实测结果 |
|---|---|
| 发布前 | 保留原发布通知 ID，只新增撤回通知。 |
| 发布后、撤回前（还未补投） | 撤回完成时即读到「撤回、发布」，不必等首次扫描。 |
| 撤回后（补投窗口内） | 首次扫描新增 2 条，显示为「撤回、发布」。 |

三种情况均再连续扫描两次，每次 `failed == ()`、新增计数为 0，读取同一用户/预警的 `(kind, id)` 序列不变。

- 同一组三项测试：在原实现上，第二种情况失败（撤回后只有撤回通知），另外两项通过；修复后 **3/3** 通过。
