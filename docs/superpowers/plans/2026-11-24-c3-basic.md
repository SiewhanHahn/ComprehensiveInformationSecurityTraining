# C3 四类基础预测实施计划

> **执行技能：** 按项使用 `executing-plans`、`test-driven-development` 和完成前验证。总计划已进入执行，不重新征询课程范围。

**目标**：干旱、高温、低温、风雹都有能编辑输入并重新计算的路径，和四类端到端预警明确区分。

**设计**：复用一页「基础预测」，以同一套地点、UTC 窗口、数值字段、结果和缺测提示承载四个模块。服务端做可重复的教学计算；页面明确输入是人工提供的预报值，内置初始值为教学示例。试算只读，不生成预警草稿，不引入数据库迁移或在线数据依赖；不修改已验收的历史档案、量化指标和正式审批。

**技术栈**：FastAPI / Pydantic、Vue 3、pytest、Node 内置测试、Playwright。

**依据**：[八灾种验收表](../../c-eight-hazard-acceptance.md)、[课程执行总计划](2026-11-24-course-execution.md)。

## 规则与验收

| 子项 | 教学输入与规则 | 必须实际演示 |
|---|---|---|
| 干旱 | 地点、窗口首日（UTC）、签发前已有连续少雨日数和未来 7 个日总降水（mm）。日雨量 `< 1.00` 延续，`≥ 1.00` 清零；第七天结束后连少雨 `≥ 14` 天判持续。 | 初始 9 天加 7 干日 → 16；改第 5 天为 1.00 mm → 剩 2；初始 7 天 → 正好 14；缺任一输入为未知。不是农业干旱预警。 |
| 高温 | 地点、UTC 起点、未来 24 个逐时气温（°C）；最大值 `≥ 35.0` 显示高温达到教学线及对应时次。 | 可将一个时次从 34.9 改 35.0，再清空该值；观察未达、达标和未知。 |
| 低温 | 同高温的输入与时间排布；最小值 `≤ 0.0 °C` 显示低温达到教学线及对应时次。 | 可将一个时次从 0.1 改 0.0，再清空；低温试算不等同寒潮。 |
| 风雹 | 地点、UTC 起点、6 个有效时次逐小时阵风（m/s）和独立的明确冰雹预报信号（有 / 无 / 缺测）。阵风最大值 `≥ 17.0`，冰雹序列有明确正信号才达标；任一分量缺测只让该分量未知。 | 只风达标、同时有雹、无雹或缺测的区分；不得以阵风代替冰雹信号。 |

## 实施批次

- [x] **C3.1 干旱**：在 `tests/test_basic_forecast.py` 先锁定 16 / 14 / 2、缺测、无效类型和 API 权限；`backend/app/services/basic_forecast.py` 接收 `DroughtInput`，计算 `DroughtAssessment`。输入字段 `location`、`start_date`、`antecedent_dry_days`、`daily_rain_mm`；登录后提交到 `POST /api/v1/basic-forecast/drought/assessment`，JSON 只返回本次计算、不入库。用 `DroughtTrial.vue` 提供可编辑的逐日字段、末日结果和缺测说明，接进 `BasicForecast.vue`。先测编辑后旧结果清空，再做浏览器正常、边界、缺测和无外站请求验收。
- [x] **C3.2 高温**：新增共享逐时温度输入、时次列表和结果卡。先测最大值与等阈、气温和窗口校验、缺时次结果；只点亮高温入口并验收。
- [x] **C3.3 低温**：复用 C3.2 窗口和字段，增加独立的最小值规则和低温入口。先测阈值方向、等阈与缺测，回归高温。
- [x] **C3.4 风雹**：共享窗和结果样式；阵风与雹信号分别计算。先测显式 `false` 和缺值 `null`、只缺一个分量、恰等阵风阈值；展示两条独立结论。
- [ ] **八种终验**：单独从干净交付包启动，通过全部八类、正式预警链路和无外网演示，核对报告、说明、答辩稿与同一版本。项目所有者此时再选开源许可，才进行最终交付推送。

每个子项以干净归档在同一个候选 SHA 上保留实测结果和截图；完成即单独 push 到 `integration/phase-c` 并核对远端标签。`BASIC` 在灾种总览单独计数，不计入 `IMPLEMENTED`。示例不写成历史原业务数据，不引用为官方标准。
